# ADR-0023: Patch Release 0.10.1

## Status

**Accepted** by Giovanni Fiore on 2026-11-13. He replied "si" ("yes") to the request
to accept ADR-0023 and publish 0.10.1.

## Context

The README clarity work is merged on `main` as follow-up within
[ADR-0015](adr-0015-run-efficiency-hardening-of-the-generated-kernel.md),
[ADR-0017](adr-0017-version-pinned-projected-invocation-and-tolerant-frontmatter-parsing.md),
[ADR-0019](adr-0019-low-risk-adr-tier-with-per-task-review.md), and
[ADR-0021](adr-0021-explicit-low-risk-tier-opt-in-for-existing-repositories.md).
GitHub already shows it. npm shows the README of the published tarball, so the
0.10.0 package page still has two defects:

- A stray quote breaks the low-risk `verify` example when it is copied.
- The page says that nothing merges unreviewed. That holds only with
  `--enforce ci` and the governance check required in branch protection.

Repositories generated by 0.10.0 carry the same overstated claim in `AGENTS.md`,
the `govern-development-task` skill, and its decision-gates reference. Those files
are kit-owned, so the fix reaches existing repositories only through a release
followed by `update`.

The release changes no code, command, or option.

## Decision

1. Release the merged documentation and wording fixes as **0.10.1** (SemVer patch).
2. Follow [the release guide](../releasing.md): move `[Unreleased]` to `[0.10.1]` in
   `CHANGELOG.md`, run `npm run validate`, run
   `npm version patch -m "chore(release): %s"` (the `version` script syncs
   `plugin.json`), push `main` and tag `v0.10.1`, and publish the GitHub release so
   `publish.yml` publishes through Trusted Publishing.
3. No file under `.github/workflows/**` changes, so the push needs no `workflow`
   token scope.

## Consequences

### Positive

- **POS-001**: The npm package page shows the corrected README: a working `verify`
  example, the accurate merge-gate guarantee, and the run-efficiency features.
- **POS-002**: `update` brings the accurate wording into the kit-owned governance
  files of existing repositories.

### Negative

- **NEG-001**: A release without behavior changes still moves the version pin, so
  every repository that runs `update` gets a small diff in its generated
  instructions, hooks, and CI.
- **NEG-002**: Existing repositories keep the old sentence in their user-owned
  `docs/adr/README.md`, because `update` never overwrites it. Owners can edit it by
  hand.

## Alternatives Considered

### Wait for the next feature release

- **ALT-001**: **Description**: Ship the corrected README with the next feature
  release.
- **ALT-002**: **Rejection Reason**: Until then, the npm page keeps a broken example
  and an overstated guarantee, and agents in generated repositories keep reading
  the inaccurate governance text.

### Replace the 0.10.0 README in place

- **ALT-003**: **Description**: Update the README of the published 0.10.0.
- **ALT-004**: **Rejection Reason**: npm never allows republishing a version, so a
  README change needs a new version.

## Implementation Notes

- **IMP-001**: After publication, verify `npm view agentic-repo-kit version` and
  the package provenance. Then confirm that the README in the published tarball has
  no stray quote and states the conditional merge gate, and that
  `npx agentic-repo-kit@0.10.1 update` on a 0.10.0 repository refreshes the pin and
  the governance wording while keeping `docs/adr/README.md`.
- **IMP-002**: Record the release in `docs/wiki/log.md`.
