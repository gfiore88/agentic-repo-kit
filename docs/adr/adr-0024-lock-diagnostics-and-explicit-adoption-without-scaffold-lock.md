# ADR-0024: Lock Diagnostics and Explicit Adoption for Repositories Without scaffold.lock

## Status

**Proposed**. Implementation waits for explicit acceptance by Giovanni Fiore.

## Context

`npx agentic-repo-kit@0.10.0 update` failed in an existing repository with
`scaffold.lock not found; this repository was not initialized by agentic-repo-kit`,
followed by advice to run `init`. The repository had been initialized with 0.6.0. It
contains `.agents/`, an actively maintained `docs/wiki/log.md`, and an `AGENTS.md`
with about 4 KB of project rules. `scaffold.lock` and `scaffold.yaml` are missing:
Git never tracked them and does not ignore them.

Reproductions with the published 0.6.0 and the current kit show three gaps:

1. **One message for three states.** `readScaffoldLock` returns `null` for a missing
   file, an unreadable file (for example `EACCES`), and content that is not a JSON
   object (for example merge-conflict markers). `update` reports all three as "not
   found" and claims that the repository was never initialized. `doctor` prints the
   raw error without a next step.
2. **No recovery path.** In a repository that has the kernel but no lock, `update`
   refuses ([ADR-0013](adr-0013-lock-aware-update-and-governance-gate-hardening.md)
   decision 2), and `init` aborts on the first divergent file. Every active
   repository diverges at least in its user-owned wiki (`docs/wiki/log.md`), and a
   repository generated by an older version also diverges in every kernel file
   changed since. The error message points to a command that cannot succeed.
3. **No reliable configuration source.** The only recovery is manual: run the
   generating version's `init` with the original runtimes in a temporary directory
   and copy its `scaffold.lock`. With that rebuilt 0.6.0 lock, 0.10.0 reported one
   conflict (the customized `AGENTS.md`), updated the unmodified kernel files, and
   removed four retired agents. With an empty baseline instead (a lock whose
   `managedFiles` is empty), it reported ten conflicts: `AGENTS.md` and nine kernel
   files changed since 0.6.0. The rebuild needs the generating version, which only
   the lock records (`kitVersion`, since 0.7.0) besides the pinned invocations of
   [ADR-0017](adr-0017-version-pinned-projected-invocation-and-tolerant-frontmatter-parsing.md)
   (since 0.8.1). It also needs the runtimes, which `scaffold.yaml` records but which
   may be lost with it. Runtime detection cannot replace them: the base kernel
   creates `.agents/agents/` and `.agents/rules/`, which are Antigravity's detection
   markers. In an initialized repository that enabled only GitHub Copilot, detection
   selected Antigravity as well, and it also reports any runtime CLI installed on the
   machine.

The change stays within the update scope of
[PRD-0005](../product/prd-0005-kernel-update-and-upgrade-command.md); following the
ADR-0013 precedent, no new PRD is required.

## Decision

1. **Precise lock diagnostics.** `update` and `doctor` distinguish four lock states,
   name the next step for each, and write nothing:
   - *Missing, no kernel*: run `init`, as today.
   - *Missing, kernel present* (`AGENTS.md` or `.agents/registry.md` exists; both
     ship since 0.1.0): restore `scaffold.lock` from version control or from the
     machine that initialized the repository; otherwise run `update --adopt`.
   - *Unreadable*: report the system error (for example `EACCES`).
   - *Invalid* (not a JSON object): report the parse error and suggest restoring the
     file from version control, for example after a merge conflict.
2. **Explicit adoption.** `update --adopt` updates a repository without
   `scaffold.lock` against an empty baseline:
   - Missing planned files are created and user-owned paths are preserved, as in
     every update.
   - Kernel-owned files equal to the plan are unchanged.
   - Every other existing kernel-owned file is a conflict, because no recorded hash
     proves that the kit wrote it. Conflicts abort the update before any write
     unless `--force` is given.
   - The update writes a new `scaffold.lock` and `scaffold.yaml`.

   It honors `--dry-run`, `--yes`, `--json`, `--force`, `--enable-low-risk`, and
   `--git-exclude`. It is refused when `scaffold.lock` exists in any state, so a
   damaged lock is restored or deleted deliberately.
3. **Explicit configuration.** Adoption takes the runtimes, enforcement, and profile
   from the flags, then from an existing `scaffold.yaml`. Without either source for
   the runtimes, it refuses and asks for `--runtime <ids|none>`, because detection is
   unreliable in an initialized repository. Enforcement defaults to `none` and the
   profile to `full`, as in `init`. When `scaffold.yaml` is the configuration source,
   regenerating it from that configuration is not a conflict.
4. **Documented recovery order.** The README documents the recovery steps:
   1. Restore the lock from version control.
   2. Otherwise, when the generating version and runtimes are known, rebuild that
      version's lock in a temporary directory, which limits conflicts to the files
      the user changed.
   3. Otherwise, run `update --adopt`.

   It also states that `scaffold.lock` and `scaffold.yaml` must stay with the
   repository: commit them, or keep the local copies with `--git-exclude`, and keep
   them out of clean-up scripts.

## Consequences

### Positive

- **POS-001**: A repository that lost its lock returns under `update` with one
  reviewed command, without hand-built kit internals.
- **POS-002**: Every lock failure names its cause and a next step that can succeed;
  `update` no longer sends an initialized repository to `init`.
- **POS-003**: The no-silent-overwrite invariant holds: without a baseline every
  divergent kernel file is a conflict, and only `--force` overwrites.

### Negative

- **NEG-001**: Without a baseline, adoption cannot tell an untouched old kernel file
  from a customized one. After a version gap most kernel files are conflicts, and
  `--force` also overwrites real customizations such as project rules in
  `AGENTS.md`. The user backs them up first or follows the rebuild path of
  decision 4.
- **NEG-002**: Kernel files that an older version generated and the current plan no
  longer contains (retired agents, dropped adapters, an old enforcement projection)
  stay on disk, because nothing proves that the kit wrote them. The user removes
  them by hand.
- **NEG-003**: `update` gains one flag, and adoption without `scaffold.yaml` requires
  an explicit runtime list.

## Alternatives Considered

### Adopt automatically when kernel files exist

- **ALT-001**: **Description**: Run adoption without a flag whenever `update` finds
  `AGENTS.md` or `.agents/registry.md` but no lock.
- **ALT-002**: **Rejection Reason**: ADR-0013 made the lock the proof that the kit
  manages the files. A kernel copied by hand or by another tool would be adopted
  without a human decision; the flag records that decision in previews and scripts.

### `init --adopt`

- **ALT-003**: **Description**: Create the missing files and a lock, and leave
  divergent files untouched.
- **ALT-004**: **Rejection Reason**: The lock would record hashes of content that is
  not on disk and leave an old kernel mixed with the new one. The next `update`
  reports the same conflicts, so the same outcome takes two commands.

### Rebuild the lock from the generating version inside the kit

- **ALT-005**: **Description**: Fetch `agentic-repo-kit@<version>` and compute its
  plan to recover the exact baseline.
- **ALT-006**: **Rejection Reason**: It adds a network dependency and runs another
  package version from inside the kit, and before 0.7.0 only pinned invocations,
  absent before 0.8.1, record the generating version outside the lock. It stays a
  documented manual path (decision 4).

### Documentation only

- **ALT-007**: **Description**: Document the empty or rebuilt lock and change nothing
  else.
- **ALT-008**: **Rejection Reason**: Users would hand-edit kit internals, and the
  error message would still recommend `init`, which cannot succeed in this state.

### Preserve user-owned files during `init`

- **ALT-009**: **Description**: Let `init` skip divergent user-owned paths instead of
  reporting them as conflicts.
- **ALT-010**: **Rejection Reason**: Kernel files changed between versions would
  still conflict, so `init` could not recover a repository generated by an older
  version.

## Implementation Notes

- **IMP-001**: `readScaffoldLock` returns the lock state (`ok`, `missing`,
  `unreadable`, `invalid`) and its error. `update` and `doctor` map each state to its
  message; `update` exits with status 1 without writing.
- **IMP-002**: `inspectUpdate` with an empty baseline already yields the conflict
  semantics of decision 2, as the reproduction showed, so adoption reuses it.
  `args.mjs` accepts `--adopt` for `update` only.
- **IMP-003**: A minimal reader for the `scaffold.yaml` format the kit writes
  (`enforcement`, `profile`, and `compatibility.runtimes`).
- **IMP-004**: Tests:
  - each lock state produces its message and writes nothing;
  - `--adopt` on a repository shaped like a 0.6.0 one (customized `AGENTS.md`,
    edited log, no lock or `scaffold.yaml`) reports conflicts and writes nothing;
  - with `--force`, it preserves user-owned files, writes the lock and
    `scaffold.yaml`, and `doctor` reports the repository healthy;
  - `--adopt` is refused when a lock exists, and without `scaffold.yaml` or
    `--runtime`;
  - `--adopt --dry-run` writes nothing;
  - the configuration comes from `scaffold.yaml` when it is present.
- **IMP-005**: Docs: the README recovery section, a changelog entry, and the kit wiki
  and log. The `[DECISION]` on lock requirements in
  `docs/wiki/architecture/kernel-and-adapters.md` changes with the implementation.
- **IMP-006**: Release as a minor version under its own release ADR, because
  `--adopt` is a new option.
