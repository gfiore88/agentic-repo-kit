# ADR-0028: Automatic Three-Way Merge of Customized Kernel Files on Update

## Status

**Accepted** by Giovanni Fiore on 2026-11-13. He chose the design (base rebuilt from
the version in the lock; conflict markers while the update continues), then, asked
how to proceed, chose "Accetto l'ADR-0028 insieme al rilascio 0.13.0" ("I accept
ADR-0028 together with the 0.13.0 release").

## Context

Since [ADR-0013](adr-0013-lock-aware-update-and-governance-gate-hardening.md),
`update` replaces a kernel file only while it still matches its locked hash. Any
other content is a conflict. One conflict aborts the whole update unless `--force`
is given, and `--force` discards the owner's changes. The lock stores hashes only,
so `update` cannot merge.

Owners customize kernel files as intended: project rules in `AGENTS.md`, agent
tweaks, and adapter instructions. Every such repository therefore hits conflicts at
every update. In a client repository, ten customized files required a manual
three-way merge with pristine trees rebuilt in a temporary directory. No npm user
should need that procedure.

Each kit version generates deterministic content from its version, runtimes,
enforcement mode, and profile. Since 0.7.0 the lock records `kitVersion` and the
hash of every file it wrote. A prototype rebuilt the files of 0.10.1 and 0.7.0 from
their npm packages: the content matched the lock hashes for 121 of 121 files in
both cases.

[ADR-0024](adr-0024-lock-diagnostics-and-explicit-adoption-without-scaffold-lock.md)
rejected fetching another version for adoption (ALT-005), because a repository
without a lock records no version. With a lock, the version is known and the result
can be checked against its hashes.

## Decision

1. **Three-way merge.** For each kernel-owned file that differs from both the new
   plan and its locked hash, `update` merges three versions:
   - the base: the content generated by the version recorded in the lock;
   - the owner's current file;
   - the new content.

   A clean merge is written like any other update. User-owned paths stay
   preserved.
2. **Verified base.** `update` rebuilds the base from the package of the lock's
   `kitVersion`:
   - It downloads the package from the configured npm registry
     (`npm_config_registry`, else the public registry).
   - It checks the tarball against the registry's `dist.integrity` hash.
   - It runs that version's own plan builder with the lock's runtimes, enforcement,
     and profile.
   - It uses a file's rebuilt content as the base only when its SHA-256 equals the
     hash in the lock.

   Packages are cached in the user's cache directory. When the lock records the
   running version, the current plan is the base and nothing is downloaded.
3. **Conflicts do not stop the update.**
   - A file whose changes overlap is written with conflict markers
     (`<<<<<<< yours`, `=======`, `>>>>>>> agentic-repo-kit <version>`) and listed,
     while every other file is updated.
   - When no base can be built, the file keeps the owner's content and is listed with
     the reason. That happens offline, without a recorded version, with a version
     missing from the registry, or with a hash mismatch.
   - `update` exits with status 1 while such files remain. `--force` keeps its
     meaning: it takes the kit's version.
4. **Unresolved markers are blocked.** `doctor` reports managed files that contain
   the kit's conflict markers as unhealthy. `verify` fails on them, so hooks and CI
   stop a commit that still contains them.
5. **No subprocess.** The merge runs in-process (a dependency-free line-based
   three-way merge) and the package is read with Node's built-in modules.

## Consequences

### Positive

- **POS-001**: A customized kernel updates with one command. Only overlapping edits
  need attention, in place, with ordinary editor or agent tooling.
- **POS-002**: One file can no longer block the whole update; every other kit change
  lands.
- **POS-003**: The base is exact: rebuilt content is used only when it matches the
  hash the lock recorded when the kit wrote the file.
- **POS-004**: Repositories initialized with 0.7.0 or later benefit at their next
  update, without migration.

### Negative

- **NEG-001**: When customized files exist and the lock records a different version,
  `update` needs the npm registry. Offline, those files keep the owner's content and
  are listed.
- **NEG-002**: `update` runs the plan builder of the version recorded in the lock.
  The code comes from a package verified against the registry's integrity hash, and
  it is the same code that generated the repository's files. The registry is
  trusted exactly as much as `npx` already trusts it.
- **NEG-003**: The merge is line-based. Edits on the same or adjacent lines conflict,
  as with Git. A file with markers can mislead agents until it is resolved;
  `doctor` and `verify` report it.
- **NEG-004**: The merge engine and the package reader are new code to maintain.

## Alternatives Considered

### Store a copy of the generated files in the repository

- **ALT-001**: **Description**: Save the content the kit writes, for example under
  `.agents/`, and use it as the base.
- **ALT-002**: **Rejection Reason**: It duplicates more than a hundred files in
  every repository and helps only from the following update. The owner chose the
  rebuilt base.

### Keep the owner's file and write the kit's version beside it

- **ALT-003**: **Description**: Leave the file unchanged and add
  `<file>.kit-new`.
- **ALT-004**: **Rejection Reason**: The owner still merges by hand, and side files
  were already rejected in ADR-0013. The owner chose conflict markers.

### Run `git merge-file`

- **ALT-005**: **Description**: Delegate the merge to Git.
- **ALT-006**: **Rejection Reason**: It needs Git on the PATH and adds a subprocess
  to a CLI that runs none.

### Keep aborting on conflicts

- **ALT-007**: **Description**: Leave `update` as it is.
- **ALT-008**: **Rejection Reason**: It is the behavior this ADR fixes.

## Implementation Notes

- **IMP-001**: A merge module implements a line-based three-way merge (LCS diff
  against the base, then the merge of both change sets). Tests cover:
  - edits on both sides that do not overlap;
  - identical edits on both sides;
  - overlapping edits;
  - appends at the end of a file;
  - CRLF line endings.
- **IMP-002**: A base module fetches the registry metadata, verifies `dist.integrity`
  (SHA-512), and extracts the tarball with `zlib` and a minimal tar reader that
  handles PAX headers. It caches the package under the user's cache directory,
  imports the plan module, and keeps only the files that match the lock. Tests serve
  a package from a local HTTP registry.
- **IMP-003**: `update` reports each file as merged, conflicted, or kept (with the
  reason), in text and in `--json`.
- **IMP-004**: `doctor` and `verify` detect the kit's conflict markers in managed
  files.
- **IMP-005**: Docs: the README update section (merge, network, `--force`), the
  changelog, the kit wiki, and the log.
- **IMP-006**: Release as a minor version under its own release ADR.
